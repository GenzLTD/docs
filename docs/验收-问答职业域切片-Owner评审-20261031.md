## 一、问题

`/v1/ask` 的章程是母舰单入口：人只说需求，后面分到已有能力。现况把它用成了聊天：

1. 问答页只传 `query` + 页内 `session_history`，不传 `active_domain`，不申请 `navigator_memory`。
2. 招呼语六域（职业/学习/生活/社交/健康/创意）、叙事六域（职业/诗/自我/身份/信任/迷雾）、Hub（任务/舰队/人格）**三套对不上**。
3. 意图 `job_match` 仍调用旧职位管线；求职 Tab 刚 Accept 的库内匹配是另一条链。
4. 默认客户端超时 10 秒；库内 match 墙钟常超过 10s，问答这条会先超时。

不收口的后果：用户在「问答」和「求职」看到两本账；再往六域扩就是空招呼。

## 二、本切片要交付的行为（验收，不是实现清单）

```text
人在问答 Tab（已登录 + ask_rag）
  -> 说求职类话（「帮我匹配职位」「有没有适合的岗位」…）
  -> 若要把简历内容送入匹配：客户端与服务端均已确认 jobseeker_core；否则停止并分别提示缺哪项授权
  -> 若尚无简历上下文：提示去求职 Tab 解析/入库，或在已获 jobseeker_core 时允许把已贴文本当简历
  -> 匹配走库内 POST /v1/jobs/match（与求职机器人同一实现）；个性化结果不进跨用户共享缓存
  -> 返回的每条 matches[].job_id 均可 GET /v1/jobs/:id → 200
  -> 人点开详情；投递与否仍由人决定
  -> 若已授予 navigator_memory：跨会话持久化后，下次打开问答能知道「上次在职业域、曾打开过这些 job_id」
```

非目标：把问答做成本地 ChatGPT；把六域一次做完；把围坐内核接到 `/v1/ask`。

## 三、可验证验收项

### 3.1 调度（A2）

| # | 项 | 通过 | 失败 |
|---|----|------|------|
| S1 | 求职意图 | 关键词或等价说法进入职业域路径，**不**进入诗词 RAG 兜底 | 问「匹配职位」却推荐诗或通用闲聊 |
| S2 | 同一匹配实现 | 问答触发的 match 与求职 Tab 的 `POST /v1/jobs/match` 是同一服务、同一 `match_status` / `LibraryJobMatchItem` 形状 | 再调 `run_job_match_pipeline` 或返回无 `job_id` 的幻觉职位 |
| S3 | 详情可达 | 结果中每条 `job_id` 执行 `GET /v1/jobs/:id` 为 200 | 点开 404 / 502，或只有 title 没有 id |
| S4 | 无简历 | 无入库简历且当句不够当简历时，**不扣匹配配额乱搜**；明确提示去求职 Tab | 空匹配当「没有合适职位」 |
| S5 | 失败可懂 | `no_fit` / `empty_library` / `unavailable` / `quota_exceeded` 与求职页同一套，不把失败显示成空白闲聊 | `matches: []` 且无状态 |

### 3.2 前端与授权（A3）

| # | 项 | 通过 | 失败 |
|---|----|------|------|
| F1 | 无新 Tab / 无新域首页 | diff 限于问答页展示与跳转、共享类型；Hub 任务列表不改 | 为六域新建页面 |
| F2 | 可点 | 有 `job_id` 的卡片跳 `pages/job-detail?id=` 或求职 Tab 已有列表 | 只有一段不可点的推荐散文 |
| F3 | 时限与超时语义 | **直接 Ask 匹配**须声明端到端时限，且 **≥ 后端库内 match 最长等待**（或与之对齐的显式异步：先返回「匹配进行中」再取结果）；若产品选择不在 Ask 内等满，则**只允许**引导用户去求职 Tab 完成，并说清原因。超时/失败须可懂。**禁止**静默回退旧 Tatha / 即席匹配管线 | 默认 10s 先失败；后端仍在算时前端空白；超时后偷偷走旧管线 |
| F4 | 授权（含 Ask 内简历） | 问答本身要 `ask_rag`。**凡简历内容（粘贴文本、已入库简历、或会进入匹配服务的 resume 字段）在送入匹配之前**，客户端与服务端均须确认 `jobseeker_core`；**仅有 `ask_rag` 不足以授权**，缺任一项则停止处理并分别提示。跳去求职闭环同样要 `jobseeker_core` | 用问答授权代替求职授权；Ask 内贴简历未授 `jobseeker_core` 仍打 match |

### 3.3 缓存隔离（Owner 门槛）

| # | 项 | 通过 | 失败 |
|---|----|------|------|
| C1 | 个性化不共享 | 请求含用户简历上下文、或响应含面向该用户的 `job_id` 匹配结果时：**绕过共享缓存**，或使用包含 **用户身份 + 简历上下文身份**（如 user_id + content_fp / resume_id）的隔离键 | 用户 A 的 query 命中用户 B 的匹配缓存；同一句「帮我匹配」跨账号串结果 |

### 3.4 记忆（A4）

| # | 项 | 通过 | 失败 |
|---|----|------|------|
| M1 | 默认不记 | 未授予 `navigator_memory` 时，关进程后再开问答，不出现「你上次在职业域」 | 偷偷持久化 |
| M2 | 授权后可记 | 授予后写入：`domain=职业域`、时间、**job_id 列表（不含简历原文、不含 JD 全文）** | 把 markdown 简历写进记忆 |
| M3 | 唯一持久化 | 跨会话记忆的**唯一真源**须在实现 PR 中钉死为**单一持久化位置**（本产品、用户隔离的存储；例如网关后账户时间线 / 叙事事件表——以代码 PR 声明为准）。**进程内 `NavigatorMemory` 不得单独充当跨会话验收依据**。禁止 Dual / circle / bridle / WP | 只写进程内存；或同时写多处且无单一真源；在 `circle.genz.ltd` / bridle 出现该记忆 |
| M4 | 召回 | 授权用户再次进入问答，助手能说出上次职业域结果可打开（点同一 `job_id` 仍 200），不把记忆当成新的匹配结果 | 用记忆冒充一次新的库内 match |
| M5 | 撤权 | 用户撤回 `navigator_memory` 后：**立即停止召回**；既有职业域记忆按实现 PR 声明的规则 **删除或等价不可恢复处置**（须可测） | 撤权后仍能读出上次 job_id 列表 |

### 3.5 红线（A5 / D5 全链路）

| # | 项 | 通过 |
|---|----|------|
| R1 | 无自动投递 | 全程无申请投递 API |
| R2 | 无围坐投票 | 职业域路径不调用 `/circle/api/*`，不把 `API_ORIGIN` 设为 `circle.genz.ltd` |
| R3 | D5 全链路 | 凡有简历内容参与的 **意图识别、调度、匹配**，未脱敏时默认本机/租户内模型；`JOB_MATCH_ALLOW_CLOUD_LLM` 未开时匹配（及会吃到简历原文的上游步骤）不出云。与求职机器人同一开关 |
| R4 | 不扩域 | 招呼语若仍列举未开的域，须标明「本切片仅职业域已接通」；不得把未实现域做成可点入口 |
