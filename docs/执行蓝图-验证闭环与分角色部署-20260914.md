## 2. 验证方法论（组织通用）

### 2.1 Dogfooding 验证闭环

架构里已埋好闭环（dsh-bridle MEMBERS.md），成员各自用自己的语料跑通它：

```
成员自有语料 → kb_import / kb_search / kb_ask（dsh）
            → px_article / px_rewrite（dsh-poetics 成稿）
            → 人审 → 博客发布 → Variety blog 展示博主优秀作品
            → 文章回灌语料 → pgvector 检索 → 辅助下一篇
```

飞轮：内容 → 验证产品 → 内容再变语料 → 检索更好 → 内容更好。

### 2.2 向量化管线（语料无关）

pgvector + HNSW + RAG 是语料无关的，换语料即可复用。`vec.poem_embeddings` 可类比成 `vec.<domain>_embeddings`。

## 3. 分角色部署架构（结合本机实测）

| 环节 | 落点 | 说明 |
|---|---|---|
| `kb_import` / `kb_search`(keyword) | 本机 | 轻，不装 torch |
| 博客发布 + Variety 展示 | 本机 | WordPress 轻 |
| pgvector 检索 | 本机 | 已装好 |
| `kb_search`(vector) | 强机器 | Chroma + torch 重 |
| `kb_ask` / `px_article` / 重嵌 | 阿里云 | 7B 模型 + torch 本机跑不动 |
| 交叉验证 | 强机器 | 与云结果对拍 |

> 本机实测边界：8GB 内存当前可用约 1.5GB，跑不动 7B LLM 与 torch embedding；轻链路（检索 + 发布 + 验证）够用。

## 4. 个人验证示例（供参照，非指令）

某成员（szpeter2026）本机选择「垂直领域知识库」方向（如特种设备标准、跨境用工法规等），以自有语料做验证。理由是有专业壁垒、有付费场景、语料已具备。

## 5. 技术边界（跨仓调研结论）

1. 本地 LLM（`qwen2.5:7b`）本机跑不动（CPU 推理需 4–5GB 内存且极慢），且 `.env.example` 约束「未脱敏材料须本地 Ollama、禁止云 Key」。
2. embedding 重：`sentence-transformers` 自动引入 torch（1–2GB）。
3. dsh-poetics 需先克隆（本地暂无）。
4. 多向量库/多模型并存：dsh 用 Chroma + nomic-embed-text，pgvector 用 text2vec-base-chinese(768)——两条线要明确边界（对齐 pgvector 落点 §4.1「model↔dim 绑定」）。

## 6. 合规衔接

- 云上 AI 环境先定位为**内部验证、标注实验性**，不对公众开放 → 暂不触发大模型备案。
- 一旦 AI 问答对公众开放 → 触发生成式人工智能服务备案（走成员分工合规线）。
- 博客内容域：个人备案 `.cn` 做专业内容展示合规，不做经营性/付费内容。

## 7. 执行路线图（分阶段）

| 阶段 | 动作 | 落点 | 验收 |
|---|---|---|---|
| P0 · 本机轻链路 | 克隆 dsh-poetics；`kb_import` 喂语料；`kb_search`(keyword)；发 2–3 篇博客；pgvector 检索 | 本机 | 轻链路通；博客可展示 |
| P1 · 云重活 | 按量 CPU 实例；Ollama(3b) + text2vec；跑通 `kb_ask` + `px_article` + 重嵌 | 阿里云 | 重活通；记录成本/耗时 |
| P2 · 交叉验证 | 强机器与云结果对拍；嵌入模型对比 | 强机器 | 结果一致；模型定案 |
| P3 · 闭环成型 | 文章回灌 → pgvector；Variety 展示；合规判断 | 全线 | 飞轮转起来 |
