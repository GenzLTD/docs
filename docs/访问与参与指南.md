# GenzLTD 架构知识库访问与参与指南

> 本仓是 GenzLTD 的架构知识库，不是业务代码仓库。它保存架构决策、系统设计、仓库血缘、运行约定和协作记录，是团队讨论、评审和追溯的共同入口。

## 1. 访问仓库

### 1.1 GitHub 网页

1. 使用已加入 GenzLTD 组织的 GitHub 账号登录。
2. 打开 [GenzLTD/docs](https://github.com/GenzLTD/docs)。
3. 首次访问若提示无权限，请联系组织 Owner 或 Maintainer 检查组织成员资格和仓库权限。

仓库地址：`https://github.com/GenzLTD/docs`

### 1.2 GitHub Codespaces

推荐使用 Codespaces 进行统一的文档编辑环境：

1. 打开 [创建 GenzLTD/docs Codespace](https://github.com/codespaces/new?repo=GenzLTD/docs)。
2. 选择仓库的 `main` 分支和默认开发容器配置。
3. 等待容器完成初始化。`post-create.sh` 会安装 MkDocs、Material 主题和 Mermaid 支持。
4. 在 Codespace 的终端执行 `mkdocs serve -a 0.0.0.0:8000`，通过转发的 8000 端口预览文档。
5. 使用完毕后停止 Codespace，避免持续占用个人或组织配额。

### 1.3 本地克隆

已配置 SSH 的成员可以执行：

```bash
git clone git@github.com:GenzLTD/docs.git
cd docs
```

没有 SSH key 时，可以使用 GitHub CLI 登录后克隆：

```bash
gh auth login
gh repo clone GenzLTD/docs
cd docs
```

不要把 Personal Access Token、`.env` 内容或其他凭据写入文档、提交信息或仓库文件。

## 2. 成员如何参与

### 2.1 先判断文档类型

| 需要记录的内容 | 位置 | 维护方式 |
| --- | --- | --- |
| 不可逆或影响多个仓库的架构决策 | `adrs/NNNN-短标题.md` | 新建 ADR，经过评审后合并 |
| 架构方案、路线图和仓库关系 | 根目录 Markdown 文档 | 更新对应文档和索引 |
| 文档站点展示文件 | `docs/` | 与根目录内容保持同步，并更新 `mkdocs.yml` 导航 |
| 跨仓库 schema 或数据同步规范 | 对应专题文档和 `scripts/` | 同步更新规范、脚本和验证说明 |

本仓不是代码实现仓。代码修改应提交到对应的业务或组件仓库，并在本仓记录需要长期保留的架构结论和链接。

### 2.2 推荐的修改流程

1. 从最新 `main` 创建工作分支，例如 `docs/onboarding-guide`。
2. 修改文档正文、目录索引和导航；新增 ADR 时遵守 `adrs/README.md` 的编号和状态规则。
3. 本地预览并执行检查：

   ```bash
   mkdocs build --strict --site-dir /tmp/docs-site-check
   git diff --check
   ```

4. 提交清晰的 commit，例如 `docs: add repository participation guide`。
5. 推送分支并创建 Pull Request，说明背景、影响范围和验证结果。
6. 等待对应 CODEOWNER review；作者不能批准自己的 PR。
7. Review 通过后合并到 `main`。合并后确认文档站点构建和链接正常。

普通成员不要直接向 `main` 推送。当前 Free plan 下部分分支保护能力可能无法由 GitHub 强制执行，但评审流程仍是本仓的治理要求。

## 3. 日常维护清单

### 每次改动

- 更新正文中的状态、日期、负责人和相关仓库链接。
- 同步文档索引；新增页面时同步更新 `README.md` 和 `mkdocs.yml` 的 `nav`。
- 使用 Markdown 标题层级，标题和列表前后保留空行。
- 检查是否误提交凭据、内部密钥、个人隐私或未经确认的事实。

### 每周或每个里程碑

- 检查 ADR 状态：`Proposed`、`Accepted`、`Superseded` 是否准确。
- 更新 `CATALOG.md` 中的仓库定位、血缘关系和主线状态。
- 关闭或标记已经完成的待办，保留决策依据和验证证据。
- 运行一次严格构建，确认导航页面和 Mermaid 图表可渲染。

## 4. 运行知识库站点

在 Codespace 或已安装依赖的本地环境中：

```bash
mkdocs serve -a 0.0.0.0:8000
```

构建静态站点：

```bash
mkdocs build --strict --site-dir /tmp/docs-site-check
```

`mkdocs.yml` 使用 `docs/` 作为站点源目录。修改根目录文档时，如果该内容需要在站点展示，也要同步更新 `docs/` 对应文件；否则 GitHub 仓库页面和 MkDocs 站点会出现内容不一致。

## 5. 权限与责任

- **Reader**：阅读、搜索和引用已合并的知识库内容。
- **Member**：创建分支、提交文档修改、发起 Pull Request 和参与讨论。
- **Maintainer / Owner**：处理评审、合并、权限、Codespace 和站点运行问题。
- **CODEOWNER**：对负责路径的修改提供必要 review；`adrs/` 由 ADR 起草主线负责，其他文档由 Owner 群兜底。

详细评审规则见根目录 `README.md` 和 `.github/CODEOWNERS`；Codespace 设计和治理约束见 `adrs/0005-remote-codespace-development.md`、`adrs/0006-docs-governance-codespace.md`。

## 6. 常见问题

### 没有仓库权限

确认 GitHub 登录账号、组织成员资格和仓库访问级别。不要通过共享账号或共享 Token 绕过权限控制，直接联系 Owner 处理。

### Codespace 启动失败

先删除已停止且损坏的实例，再从仓库页面重新创建。若仍失败，记录创建时间、分支、完整错误信息和 Codespace 名称，在 Issue 或团队协作频道中反馈。

### 站点构建失败

先执行 `mkdocs build --strict` 获取完整错误。重点检查 `mkdocs.yml` 中的导航路径、`docs/` 下文件名大小写、Markdown 链接和 Mermaid 代码块；修复后再次构建并把结果写入 PR 描述。

### 不确定该改什么

先查 `README.md`、`CATALOG.md`、`adrs/README.md` 和相关 ADR。若仍无法判断，先开 Issue 描述背景和候选方案，再开始正文修改。

## 7. 反馈与改进

知识库本身也需要持续维护。任何成员都可以通过 Issue、Pull Request 或评审评论提出：

- 过期、冲突或缺少来源的架构结论；
- 失效的仓库链接、导航项或运行命令；
- 新成员无法理解的术语、流程和上下文；
- 需要形成正式 ADR 的跨仓库决策。

每次改进都应留下可追溯的 commit 和评审记录，让下一位成员能够沿着历史继续工作。
