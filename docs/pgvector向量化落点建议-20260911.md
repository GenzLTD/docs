## 一、三张表处置（直接回答）

| 表 | 进 PG 业务库 | 进 pgvector 向量层 | 理由 |
|---|---|---|---|
| `sqlite_sequence` | ❌ 否 | ❌ 否 | SQLite `AUTOINCREMENT` 内部记账表，无业务语义。PG 对应物是 **sequence 对象**（`BIGSERIAL` / `GENERATED … AS IDENTITY` 自动创建），**不是表** |
| `signal_outbox` | ✅ 是（R2 上线时） | ❌ 否 | 事务性发件箱：按 `status` 扫队列、按 `nonce` 精确取。**访问模式全是精确谓词与队列扫描，没有相似度检索需求** |
| `signal_dlq` | ✅ 是（R2 上线时） | ❌ 否 | 死信队列：同上；且 `replayed_at` 落定即终结，属短生命周期运维表 |

**一句话**：这三张表与向量化**没有关系**。`sqlite_sequence` 应从所有表数对账口径中剔除；`signal_outbox` / `signal_dlq` 是业务运行态表，进 PG 业务 schema，但不进向量层。

### 1.1 对账口径（立即可用的一个修正）

表数一律按「业务表」计：

```sql
select name from sqlite_master where type='table' and name not like 'sqlite_%';
```

按此口径：**Vultr 生产 50 / 天翼 50 / 本机 dev 52 / schema_v0.2 50**。dev 的 +2 是 R2 前瞻，不是分叉（见 [90天主线作战清单.md](90天主线作战清单.md) §3.1）。

## 二、`signal_outbox` / `signal_dlq` 进 PG 的转换要点

以本机 dev 库实测 DDL 为源，PG 侧建议形态（示意，实际以 R2 上线时的迁移脚本为准）：

```sql
CREATE TABLE signal_outbox (
    id           TEXT PRIMARY KEY,
    nonce        TEXT NOT NULL UNIQUE,
    signal_type  TEXT NOT NULL,
    body         TEXT NOT NULL,                      -- 见 2.1，严禁 JSONB
    status       TEXT NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','delivered')),
    attempts     INTEGER NOT NULL DEFAULT 0,
    last_error   TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    delivered_at TIMESTAMPTZ
);
CREATE INDEX idx_signal_outbox_status ON signal_outbox(status, created_at);

CREATE TABLE signal_dlq (
    id           TEXT PRIMARY KEY,
    nonce        TEXT NOT NULL UNIQUE,
    signal_type  TEXT NOT NULL,
    body         TEXT NOT NULL,                      -- 同上
    reason       TEXT NOT NULL
                 CHECK (reason IN ('permanent_4xx','network_error')),
    attempts     INTEGER NOT NULL DEFAULT 0,
    last_error   TEXT,
    moved_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    replayed_at  TIMESTAMPTZ
);
CREATE INDEX idx_signal_dlq_moved ON signal_dlq(moved_at);
```

### 2.1 最容易踩的一脚：`body` 必须保持 `TEXT`，不可转 `JSONB`

`body` 存的是**逐字节重发的原文**（`gfcc_fanout._post_body` 原样 POST，签名覆盖 raw body）。`JSONB` 会规范化键序与空白 → **重放时对端验签必然失败**。这是 R2 迁移的硬约束；与「PG 侧尽量用原生类型」的一般偏好冲突时，以本约束为准。

### 2.2 其余转换

| dev（SQLite） | PG |
|---|---|
| `created_at TEXT DEFAULT (datetime('now'))` | `TIMESTAMPTZ NOT NULL DEFAULT now()` |
| `status TEXT DEFAULT 'pending'` / `reason TEXT` | `TEXT NOT NULL` + `CHECK` 约束 |
| `id TEXT PRIMARY KEY` | **保留 `TEXT`**（与 `users.id` 等全套 TEXT 风格一致，不为这两张表引入 `BIGSERIAL`） |
| `nonce TEXT NOT NULL UNIQUE` | 原样保留（幂等键，精确匹配语义） |
| `idx_*` 索引 | 照搬 |

### 2.3 同批补齐

`llm_usage.cached_tokens INTEGER NOT NULL DEFAULT 0`（dev 已有，生产与 schema 未有），属同一批前瞻，随 R2 一起补。

## 三、向量层设计建议

### 3.1 不在业务表上加 vector 列

`genzltd_schema_v0.2.sql` 的核心价值是**与 `manager.py` 真源同构、可逐表对账**。一旦在业务表里加 `vector` 列，这条对账基线即失效。

**建议**：向量层与业务层物理隔离——同库不同 schema（`biz.*` 保持 50 张同构 / `vec.*` 放向量表），或独立库（由 `cortex-mcp` 自管）。

### 3.2 若确需语义检索信号，另立表

```sql
-- vec.signal_embeddings（示例）
CREATE TABLE vec.signal_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    ref_table   TEXT NOT NULL,        -- 'signal_outbox' / 'signal_dlq' / 归档表
    ref_id      TEXT NOT NULL,
    signal_type TEXT,
    embedding   vector(768) NOT NULL, -- 维度必须与模型绑定，见 4.1
    model       TEXT NOT NULL,
    dim         INTEGER NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- **不要**在 `signal_outbox` 上加 `vector` 列——那是把「会被清空 / 重放的队列表」与「长期资产」焊死，必然产生「行已删除、向量仍在」的一致性债；
- 嵌入对象应是**解包后的语义字段**（`personality_type` / traits / 摘要），**不是原始 JSON 信封**；
- `signal_*` 表生命周期短，若要长期留向量，应关联**归档表**而非队列表本身。

### 3.3 诗词等大语料同理

不要把 `poems` 在 PG 里加一列 `vector` 当作「向量化完成」。向量是**派生数据**（有模型版本、需整体重嵌），必须与真源解耦——本机 demopeter 刚经历过 nomic → text2vec 全量重嵌，若向量与真源同表，重建即灾难。

## 四、起步门禁（启动前必须先过）

### 4.1 先定维度并写死

| 来源 | 模型 | 维度 | 依据 |
|---|---|---|---|
| 90 天清单 §三「向量化脚本」 | `text2vec-base-chinese` | **768** | 本机实测（能力已验证） |
| `cortex-mcp` 侧（若采用） | 本仓**未记载**，需实测确认 | 待核 | 架构设计决策③只写「pgvector 混合召回」，未写模型 |

**model ↔ dim 必须绑定**，表定义写死（如 `vector(768)`）。建议加登记表：

```sql
CREATE TABLE vec.embedding_models (
    model_name TEXT PRIMARY KEY,
    dim        INTEGER NOT NULL,
    note       TEXT
);
```

混用 768 / 1024 会直接报错或被迫分表——**这是重建后才发现代价最高的一项**。

### 4.2 `CREATE EXTENSION vector` 可用性先验证

`genzltd_schema_v0.2.sql` 中**既无 `CREATE EXTENSION`、也无 vector 列**。ServBay 自带 PG **未必含 pgvector**（需单独安装），应在重建 PG 之前先确认：

```sql
select * from pg_available_extensions where name = 'vector';
```

属**重建前门禁**，不是重建时才处理的问题。

### 4.3 索引形态

- 向量列建 **HNSW**（pgvector ≥ 0.5）：`USING hnsw (embedding vector_cosine_ops)`，给出 `m` / `ef_construction` 默认值；
- 文本侧另建 FTS 列，检索走**向量 + FTS 的 RRF 融合**（对齐架构设计决策③的语义）。
