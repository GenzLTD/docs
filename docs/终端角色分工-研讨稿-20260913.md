## 0. 一句话

> **生态里的每个「终端」不是某个产品的功能模块，而是一个自治节点。**
> **未来工作按「终端角色」分工：一个终端，一段职责、一份边界、一条信号通道。**

---

## 1. 为什么提这件事

### 1.1 现状：分工维度缺一层

当前组织的分工维度有三套，各有用途，但**都没有表达"谁是这个节点的主权方"**：

| 维度 | 出处 | 表达什么 | 缺口 |
|---|---|---|---|
| 按仓库 | `ZERVI_GENZER_IMPLEMENTATION.md` §7 | 代码落在哪个仓 | 一个仓可能承载多个终端；一个终端可能跨多仓 |
| 按组 | 同上 §7「体验组认领」（G0 / PlanetX 组 / G4 / 海外组） | 人力资源归属 | 组是人的编制，不是运行时的节点 |
| 按战略线 | 同上 §3–5（Line 1 身份 / Line 2 裂变 / Line 3 信任） | 目标与依赖顺序 | 战略线是「做什么」，不是「谁在跑」 |

### 1.2 生态的既有定调：多个产品、一部信号宪法

`POST_DEPLOY_RESILIENCE_BACKLOG.md` §5 对这件事的原话是：

> 与经典微服务的差别：那些是**一个产品切进程**；我们是**多个产品、一部信号宪法**。
>
> 理念：**联邦 + 契约优先。传输可以很近（内环），主权不能近。人是闭环，软件是放大器。**

同文 §0 已拍板的三条纪律：**各自发育**（不共享 SSO、不共享库、不做 API 级硬绑，**同机 ≠ 同系统**）、**种子期不抄**（ActivityPub 身份图、Nostr 多中继、链上/SBT、为方便而合并登录）、**硬化（R1–R6）在部署验收前不实施**。

`TEAM_DISCUSSION_GENZER_TERMINAL_2026-07-12.md` §4 则给了节点侧的表述：

> DemoPPI = **千千万万的终端机，分布全网**；PlanetX = 游戏化封闭世界；跨域协作 = **信号收发**（非共享 DB、非统一 Auth）。

**→ 这套架构语言已经存在于生态文档，但组织分工文档里没有对应层。本文补这一层。**

## 2. 术语定义（先钉死，避免歧义）

| 术语 | 定义 | 不是 |
|---|---|---|
| **终端（Terminal）** | 一个**自治节点**：有自己的用户、自己的数据主权、自己的演化节奏；通过信号层与其他终端协作 | 不是「产品的功能模块」；不是「一个代码仓库」 |
| **内核（Kernel）** | 信号真源与共识机制（如 GFCC 内核 :5211） | 不是终端（无独立用户面） |
| **能力层（Engine）** | 被多个终端复用的底层能力（Looma / 信任层） | 不是终端（不直接面对用户） |
| **信号（Signal）** | 终端之间的**行为事件**交换（`consensus_match` / `personality_beacon` 等），薄信封 + HMAC 验签 | 不是 REST 数据同步、不是共享数据库 |
| **书架** | 门户侧对博主优质篇目的**聚合展示 + 链回原文** | 不是 CMS、不是内容镜像、不做双写 |

> **「书架」此前在组织文档中无正式定位条目**——它只存在于架构安排与口径表述。
> 既有口径（源自 `szbolent.cn` 8081 站点 `<title>` 原文）：
> **「作者博客 — 独立站点；深伯乐门户仅展示其中部分优质篇并链回原文」**
> 本文 §3 给「书架」补上正式条目，供评审。

## 3. 终端角色清单（提案）

按**生态位置**分为五类终端 + 两类非终端设施。

### 3.1 内容侧终端

| # | 终端角色 | 形态 | 承载谁 | 核心职责 | 明确不做 |
|---|---|---|---|---|---|
| **T1** | **门户终端（书架）** | Vue3 SPA + headless WP（`/wp-json`） | 访客、读者、商务访客 | 内容聚合与**链回原文**；品牌与资质背书；诗词/AI 体验入口 | 不搬内容、不双写 CMS、不做支付主路径、不扩业务后台 |

## 4. 终端之间的生态闭环（本文的需求侧论证）

### 4.1 从「博客主」看这条闭环

一位博客主同时具备两种身份：**布道者**（有内容、有受众）与 **知音需求方**（要找同频的人，且有线下交往需求）。这两种身份分别对应两个终端：

```
                    博客主（T2 自治节点 / 布道者）
                            │  写文章 = 认知输出
                            ▼
                  书架（T1 门户终端）
             只给摘要 + 链回原文，不搬内容
                            │  被读者看见
                            ▼
                       读者 = 潜在知音
                            │  内容已建立信任
                            ▼
             PlanetX 终端（T3）人格测评 → 认知输入层
                            │  舰队 / 匹配
                            ▼
             genzer 终端机（T4）共识匹配 → 价值习得层
                            │  consensus_match 信号回传
                            ▼
                 线下交往 / 真实协作（人是闭环）
                            │
        博客主获得验证 + 新受众 + 新素材 → 更强的布道动力
                            │
        └──── 受众中有人成长为新的博客主 → 节点复制
```

**关键判断**：这条链上每一跳都是**跨终端信号或跳转**，**没有任何一跳是"共享数据库"或"统一登录"**——它是 §1.2 那套联邦纪律的自然结果，不是设计妥协。

### 4.2 三环映射（与既有生态文档对齐）

`ECOSYSTEM_SIGNAL_ADAPTER_GUIDE.md` §2.2 的"托马斯三环"在终端视角下：

| 环节 | 驱动终端 | 产出 |
|---|---|---|
| 认知输入层（类课前预习） | T3 PlanetX + T4 genzer | 「我是谁、我属于谁」 |
| 价值习得层（类课中互动） | T3 PlanetX + T1/T5 | 实际职业价值 |
| 传播输出层（类课后测评） | T1/T2 + T4 | 品牌背书 + 裂变传播 → 回流 |

同文 §3.3 已标明的**唯一缺口**：**PlanetX ↔ genzer 的信号层**（`consensus_match` / `personality_beacon`）——`action_type` 与 `mission-complete` 接口均已预留，**Terminal Adapter 未实现**。

### 4.3 自裂变的真实卡点（必须点名）

「每位博主带自己的受众进来」这条链，当前**发得出去、核销不了**：

| 卡点 | 依据 | 后果 |
|---|---|---|
| PlanetX 落地**不消费** `?ref=`（只认 `?join=`，`register()` 无邀请字段） | `GROWTH_PORTAL_NAMING.md` §8.2 标 **P1-阻塞** | 博主带真码也无归因 |
| Looma `/use` 是**一次性码**（`used_by IS NULL` 用完即 404） | 同上标 **P1**（渠道码 `max_uses`/campaign 未实现） | 博主发的是"全站一个码"，一人占掉 |
| genzer 信号适配器未实现 | `TEAM_DISCUSSION` §7.2 | 「知音 → 线下」这一段没有载体 |

> **纪律（沿用原文）**：两处都动之前，**不得把固定 `ref` 当生产归因**，也不得用一次性码冒充渠道码。

## 5. 分工方案（提案）

### 5.1 分工口径

**以终端为归口单位**，每个终端一份职责卡：

| 字段 | 含义 |
|---|---|
| 终端角色 | §3 的 T1–T7 |
| 主权方 | 谁决定这个节点做什么、不做什么 |
| 交付物 | 该终端的可用形态（不是"代码"，是"能跑起来的节点"） |
| 边界 | 明确不做的清单（比做什么更重要） |
| 信号通道 | 与其他终端交换什么信号 |
| 不变量 | 该终端永不让渡的东西 |

### 5.2 职责卡（草案，待认领）

| 终端 | 主权方 | 交付物 | 关键不变量 |
|---|---|---|---|
| **T1 门户/书架** | 待认领 | 聚合展示 + 链回原文可用；`blog-kit` 与门户解耦 | 不搬内容、不双写 CMS |
| **T2 博客侧节点** | 博主本人（范式由组织开源维护） | **可独立分发的范式包**：独立主题、组件包、安装脚本、LICENSE、版本号 | 博主主权：域名/库/内容归博主 |
| **T3 PlanetX** | 融资主线（增长故事） | 人格测评 + 裂变链 + `?ref=` 归因 | 不嵌入 genzer 逻辑 |
| **T4 genzer** | 待定（见 §6） | 本地 `consensus_match` 闭环 + ingress/egress | 不共享 PlanetX DB；不提前上链 |
| **T5 T空间** | 融资主线（变现故事） | 合伙人工作台 | 去企业化口径 |
| **T6 围坐** | GFCC 线 | 圈/共识/地板可用 | 重启不清场 |
| **T7 Zervi 终端机** | 新一代智能大脑线 | 边缘运行时 + 端云路由 | 端侧隐私、断网可用 |

### 5.3 执行主体（人 / AI 协作方）

> 本节是本文提请研讨的**新增安排**，需组织确认。

**提案**：执行主体按**终端归口**承接工作，而不是按"任务类型"（写代码 / 写文档 / 做调研）承接。理由：

1. **边界可比对**——每个终端有 §5.1 的职责卡，接手方可自证"我做的属于这个终端"；
2. **避免跨终端污染**——遇到"要不要顺带打通一下"时，答案是查该终端的"明确不做"清单；
3. **验收可复述**——一个终端的交付物是"能跑的节点"，不是"改了多少文件"。

**AI 协作方的三条附加边界**（对齐 ADR-0011 与 AGENTS.md）：

| 边界 | 说明 |
|---|---|
| 组织口径门控 | 回答组织状态/优先级前，本地 `GenzLTD/docs` 必须匹配 `origin/main`，再 grounded 检索；**说不出 SHA / 路径 / Status 即视为瞎说** |
| 不越权决策 | Proposed / 「未记载」不得当成 Accepted；本类研讨稿的 §8 待决项由决策人拍板 |
| 不代签 | 走 PR 评审，作者不 approve 自己的 PR（CODEOWNERS 见 `docs/README.md`） |

## 6. 与 90 天主线的关系（**本文最需要拍板的一节**）

### 6.1 张力：T1/T2/T4 在处置清单里

`聚焦决策-Career-Cosmos-90天.md` §三原文：

### 6.2 三条路径（供研讨选一）

| 路径 | 含义 | 代价 | 与决策理由是否冲突 |
|---|---|---|---|
| **A 严格归档** | T1/T2/T4 一律不动；终端角色分工**只覆盖四拼图**（T3/T5 + 两设施） | 无额外成本 | 不冲突，但「博客主闭环」全线搁置 |
| **B 最小解冻（服务增长）** | T1+T2 作为 **PlanetX 增长故事的获客入口**解冻；T4 维持暂停 | 需投入少量人力打磨范式包 | **不冲突**——PlanetX 的角色本就是"增长故事：用户从哪来" |
| **C 全量解冻** | T1/T2/T4 全开，作为独立终端生态独立排期 | 与"7 人养不起"直接对冲 | **冲突** |

### 6.3 起草人建议：**B**

理由（对齐已决策主线，不新增叙事）：

1. `聚焦决策` 给 PlanetX 的定位是「**增长故事——用户从哪来、数据从哪积累**」。而 T1/T2 正是**内容侧的获客入口**，位置上属于"增长"的**前置件**，不是新主线；
2. 该路径**不调用四拼图之外的排期资源**——博客侧范式以"开源分发"形态存在，维护成本主要在**范式包一次性打磨**，而非持续运营；
3. T4（genzer）维持暂停，符合"7 人养不起"；其缺口（信号适配器）**不阻塞** T1/T2 跑通"内容 → 测评 → 归因"的前半段；
4. `?ref=` 归因是**T3 自有工作**（P1-阻塞），与 T1/T2 解冻与否无关——**不应以"门户还没打通"为由拖延 T3 的 P1**，也不应以"T3 还没打通"为由把 T1/T2 永久归档。
