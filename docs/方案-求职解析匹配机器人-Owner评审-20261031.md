## 一、问题

当前求职闭环在两端已经开口，但中间是两次人工编排：

1. 用户（或联调的人）在小程序求职 Tab 贴简历，点「解析」。
2. 再切到「匹配」，再贴一次（或再点一次），拿到页内 JSON。
3. 职位列表 / 详情走 **库内真实职位**；匹配走 **LLM 即席、不查库**。两条路不是同一条链。详情页源码已写明此偏差，混放会误导预期。

Mac 上刚跑通的 ServBay 消费端流水线（docx → bridle → poetics → WP 草稿）解决的是 **诗词成稿批处理**，不是求职请求。若把小程序打到那条链，等于强迫前端改成博客 inbox，并与 ADR-0011 冲突。

Owner 意图（本会话核对）：做成自动机器人，避免每次手动实现解析与匹配；小程序前端 **无必要重投入开发**。

## 二、现况锚点（拍板时不要回退）

| 锚点 | 现况（2026-10-31 Mac 联调） |
|------|------------------------------|
| 小程序求职 Tab | `pages/career`：`parse` / `match` / `jobs/list`；解析成功 thin-ingest；匹配结果仍留页内 JSON |
| 职位详情 | `pages/job-detail`：`GET /v1/jobs/:id`；库内 `documents.metadata.parsed` 透传；**匹配入口不放在本页** |
| 网关 | `zervi-rust` api-gateway `:3333` → resume `:3003`、job `:3004` |
| `POST /v1/jobs/match` | `job-service` 把 `resume_text` 截断后丢给 LLM，要 `matches` JSON；**不读职位表** |
| 消费端编排器 | `/Applications/ServBay/www/orchestrator`：inbox `poems[]` → WP draft；doctor FAIL 0；与求职账本分离 |
| 简历合规 | 信任层 / 自述验证走既有探针文档；**不是**本机器人的交付物 |

成功判据仍是产品五条：记得住、协商得了、兑得现、人往高处走、AI 不抢戏。机器人不得改这些，也不得改登录壳与支付弹窗。

## 三、建议方案

复用编排器的 **工序**，不复用其 **仓与出口**。

```text
小程序求职 Tab（现有 UI，契约不变）
  -> POST /v1/resume/parse          解析 + thin-ingest（已有）
  -> 服务端内部衔接
  -> POST /v1/jobs/match            对库内职位 retrieve
  -> 结构化 matches[]（含 job_id，可跳详情）
  -> 可选 remember（cortex，合规挂钩）
人审：用户看列表/详情；不自动投递
```

| 编排器工序 | 求职机器人落点 | 明确不落 |
|------------|----------------|----------|
| inbox | 求职 Tab 已有粘贴/提交 | `www/inbox` 诗词 JSON |
| retrieve | job-service 对 **已入库职位** 检索（PG `documents` / 既有 list 面） | 把简历灌进 dsh-bridle |
| write | 匹配理由、缺口、改简历建议（JSON，给现有 career 页） | poetics「文化赏析」、WP HTML |
| draft | 匹配结果挂在该用户简历记录上，等人打开详情 | `wp_posts` / `myblog-pipeline` |
| log | 可选 cortex remember（已发生的匹配，须过合规） | 把对话写成 Accepted 事实 |
| doctor | 网关 / PG / 模型可用性（既有服务健康） | MySQL 3306、generate.py |

### 3.1 前端契约冻结（对应 D2）

小程序继续只认：

- `careerApi.parse(text)` → `/v1/resume/parse`
- `careerApi.match(resumeText)` → `/v1/jobs/match`
- `careerApi.jobs()` → `/v1/jobs/list`
- 详情 → `/v1/jobs/:id`

允许的前端改动（若 D2 同意）仅限 career 页展示：`matches[].job_id` 存在则 `navigateTo` 详情，与列表同一套详情页。不做新 Tab、不做新设计系统、不做独立「机器人控制台」。

### 3.2 match 响应（建议，Accept 后才可改契约）

在现有 `{ matches, total_evaluated }` 上约束数组元素至少含：

- `job_id`：库内 id，可进详情；无 id 的幻觉职位丢弃或标 `unverified`
- `title` / `score` / `reasons[]`：给页内摘要
- `gaps[]`：可选，AI 不抢戏——理由服务于人决策，不代替投递

即席 LLM 生成「库里不存在的公司/职位」视为缺陷，不视为功能。

### 3.3 自动化边界（对应 D4）

- **做**：一次授权提交后，parse → ingest → match 在服务端连续完成；失败可重试，不要求用户再实现一遍。
- **不做**：自动向雇主投递、自动改用户简历并发布、自动把匹配结果发到博客或外部渠道。

## 四、明确不做（越界清单）

| 不做 | 理由 |
|------|------|
| 小程序求职 UI 重做 | 入口已在；重做与 Owner「无必要重投入」相反 |
| 把请求打到 ServBay orchestrator | 诗词批处理；出口是 WP；账本不是求职者 token |
| 简历导入 dsh-bridle / 建人才知识库 | [ADR-0011](adrs/0011-dsh-bridle-freeze-career-cosmos.md) 第 2、29 条 |
| 用本方案代替信任层「声明验证」 | 见简历探针文档；本方案只做解析与库内匹配 |
| 未脱敏简历出域（云 DeepSeek 等） | 与 bridle/poetics 口径一致：未脱敏走本机/租户内模型 |
| App Store / 微信开放平台上架材料自动化 | 另一条轨道，不混进本方案 |
| 当作 90 天融资主线新战役 | Career Cosmos 仍以聚焦决策为准；本方案是既有求职口的服务端收口 |

## 五、合规与模型

- 调用前仍走小程序已有 `ensureConsent('jobseeker_core')`；服务端继续按既有 Auth / 日配额（`Resource::JobMatch`）。
- 简历是 PIPL 敏感个人信息：存 resume-service 既有表，不复制到 www 编排器状态文件，不进诗词 inbox。
- 模型选择仍按部署区（`DEPLOY_REGION`），不按访客 IP；海外不得回落到 DeepSeek。本方案不推翻既有判断。
- 匹配理由必须能指回库内 `job_id`；指不回则降级为「未验证」，避免黑箱推荐。

## 六、建议验收（Accept 之后才开工）

技术：

1. 同一份简历，只提交一次，响应内同时有 parse 产物（或已 ingest 的 resume_id）与 `matches[]`。
2. `matches[].job_id` 均可 `GET /v1/jobs/:id` 200；抽检无 id 的项为 0，或显式 `unverified`。
3. 停 job-service 时，小程序行为与现网一致（错误/空库），不出现「机器人专用」新错误语义，除非契约 PR 写明。
4. 小程序无新页面；career 页若改展示，diff 限于匹配结果可点进详情。

产品：

5. 人仍决定是否投递；AI 给理由与缺口，不给「已投递」。
6. 与 iOS 求职面同一组接口（career 页注释已对齐 looma 接口），一端改契约必须两端一起改。
